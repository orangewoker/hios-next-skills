# 异常演练：超时、孤立记录与三种恢复条件

**本例是离线模拟，未触发任何真实超时、平台写入、生成或费用。** 逻辑 ID、检查点、回执情形与金额仅为给定条件；没有编造可调用工具或真实定位。它演练已授权工作中断后怎样续作，不是以模拟证明平台恢复能力。

触发为新会话、提交返回不明、正文保存后索引未更新，或用户问当前进度。输入为可再次找到的项目入口、最新已提交检查点、提交前操作记录、版本索引、未决 Attempt 与授权账。没有可信入口时先明确定位缺口，不能靠会话记忆声称恢复成功。

## 1. 超时前留下的模拟事实

Project P-repair；Checkpoint CP-7 指向 Scene S-repair v2、J-master v2、已验收的身份/空间用途。操作登记 OP-M-3 已保存并回读，内容包括拟提交请求、A-M-3、J-master v2、引用版本及最大费用预留。随后提交发生超时，未取得可确认受理与产物的回执，A-M-3 为 unknown。

假设批次虚构预算300元，可信消费80元，A-M-3 最大预留60元。剩余允许提交量为160元。它已计入发起的尝试，不能因超时从次数或金额账里消失。

恢复时先沿[状态恢复](../core/04-state-recovery.md)读取入口和操作登记，再依[提交核对](../generation/05-submit-reconcile.md)使用当前入口确实提供的查询路径。日志中的进度文字、模糊同名节点或模型自述不能补成终态。

## 2. 有限核对后的具体分支

| 真实入口可能返回的证据（本例假设） | 可作决定 | 不能做什么 |
|---|---|---|
| 明确回执指向 A-M-3 所属请求，且有实际终态/产物 | 保存回执、产物与历史不确定性；按真实状态更新，再观察用途 | 执行成功不等于质量合格 |
| 明确显示仍在运行 | 保留 running 及费用占用，按当前查询规则安排后续核对 | 查询上限到达不等于任务 failed |
| 终态确认为失败/取消 | 保存实际证据，另核对计费 | 失败/取消不证明未扣费，不自动释放全部预留 |
| 查询无结果、入口没有所需检索或返回无法关联 | 保持 unknown，记录已核对路径与缺口，停止受影响链 | 不把“没查到”当成没提交，不盲重发 |

假设本批只允许最多3次核对读取且该入口确已证明这些读取不收费；三次都无法确定时就保存检查点停止追加查询。这是演算的有界策略，不是 LibTV 推荐轮询次数。真实节奏、上限和查询费用来自确切契约与授权。

A-M-3 的真实末态接续任务 J-follow 需要其 Take，必须等待。独立的静物任务 J-prop 已有自己的合格资产，且虚构上界40元；在可信预算160元内可以继续规划，若其所有真实执行条件满足则可提交，之后总未决预留为100元、剩余允许提交量为120元。不能把主镜预留60元借给它。

若当前只有用户的“进度怎么样”，本轮只回读和报告，不把 J-prop 的可执行性解释为请求新提交。用户要求“继续制作”且既有授权覆盖时，才按路由选择独立工作；不会重新逐镜索批准。

## 3. 三种存储恢复条件

以下处理的是“保存记录时响应或索引更新丢失”，与生成任务查询是两个问题。**按已知 ID 回读不等于能发现未知 ID 的孤立记录。**

### 条件 A：新正文定位已知，索引仍指旧版

给定 OP-scene-2 已记录拟写 S-repair v2、旧v1及已收到的新正文定位；CP-7 仍指v1。恢复会话从操作登记取得已知定位，回读完整v2内容，核对所属项目、版本、源依赖和结束标记。内容一致后，完成索引提交并保留旧检查点；发现截断或内容不同则不晋升，保留具体差异。

可浏览产物是“v2正文核对结果＋补提交的索引＋旧CP引用＋下一步”。这条路径可以在仅支持已知ID读取时成立，但不证明未知ID发现能力，也不把多步写入称为原子事务。

### 条件 B：创建回执丢失，但有可靠的项目内检索

给定 OP-scene-3 在创建前已保存唯一操作标记和预期内容，新记录已可能创建但ID未知；本入口已验证可在本项目内按该标记搜索/枚举候选。恢复从已知 OP 取标记，用真实支持的检索条件找候选，并核对项目、操作标记、版本、完整内容与依赖。

只有唯一且完全匹配的对象可认领，补登记其真实定位后再完成索引提交。多候选不得任取第一条；逐项比较或保留歧义。无结果也不能证明不存在，保留未决。此过程中不重新创建同一正文。

可浏览产物是“检索范围/条件与候选证据＋唯一性和内容核对＋补定位/索引结果”。正式实验需让恢复会话不知道创建回执，不能偷偷使用同会话记忆的 ID 充作搜索成功。

### 条件 C：创建回执丢失，只有已知ID读取

给定新记录ID未知，入口没有已验证的项目内检索，也没有创建回执恢复能力。即使旧索引和操作登记能读，也不足以找到孤立的新记录。结论是这条恢复路径未通过；保留操作未决、旧检查点和缺失定位，不能猜ID、重复创建或请用户抄回全表作为正常恢复流程。

可继续的工作限于不依赖该记录、且有可信源状态的研究/设计或独立范围。如果索引/授权本身也不可信，暂停受影响提交。由Agent在当前网页会话实际可见的回执或项目检索能力中核对，缺失时说明是哪项记录无法定位；不转向外部会话API，也不向用户索取开发者工具资料。首次初始化也有同样问题：若最初入口不可再次定位，就不能宣称已经获得可恢复项目。

## 4. 版本改变与旧结果晚到

在 A-M-3 未决期间，用户明确修改动作顺序，J-master v3 替代v2。A-M-3 仍属于v2，保持费用与真实状态；不能因新版本出现就改写为失败或已取消。若平台有真实取消能力，按授权调用并核对回执；文档没证据不能写一个想象的取消命令。

随后旧结果晚到：保存到v2来源下，核对其实际费用；按v3用途重新审查可复用范围，但不得自动覆盖当前 Job/Timeline。旧版若仍有不受顺序改变影响的身份画面，可单独登记复用资格；不能因此视整段动作也符合新目标。

再次提交相同请求建立新 Attempt；修改输入则新 Job 版本再建 Attempt。假设授权最多5次生成尝试，此前已知2次，加 A-M-3 为3次，再提交独立 J-prop 为4次，余1次。新建 J-master v3 不把累计次数归零。

unknown 本身不能靠普通“重试”解除。同请求重发只有在用户另行明确接受可能重复扣费，并给出新尝试的金额/次数边界时才可能追加Attempt；若修改输入形成独立新Job，可在既有授权和余额范围内推进，但必须说明旧请求仍可能完成/扣费；若新任务必须消费旧结果，则继续等待或停止。旧请求仍未决且继续占用预留。这是现实出现该分支时的条件，不是本例请求付费许可。

## 5. 恢复后的可浏览报告

> **已恢复：**从已知入口回读CP-7及操作记录，当前创作目标为J-master v3。  
> **未决：**A-M-3属v2，仍unknown，虚构60元预留保留；有限核对未能确定回执。  
> **可以继续：**依据可信源的设计；J-prop若仍在授权内且用户要求继续，可按独立依赖推进。  
> **必须等待：**消费A-M-3实际末态的链；未知ID孤立正文在条件C下不能自动认领。  
> **下一步缺口：**所列请求的真实回执/可靠检索，以及未通过的记录定位能力。

以上仍是报告示范，不是本轮实际恢复结果。正式记录应附真实定位与回读；没有相关证据的部分不能写成“已恢复”。

## 检查与来源边界

走查应发现：未知提交保留预留；查无结果不重发；独立工作不能消费未决额度；纯进度不触发生成；两种ID恢复能力分开；晚到旧结果不晋升；跨Job版本累计尝试。任一项不成立就回相应责任模块，不在例子里复制第二套状态机制。

[AWS](../evidence/01-sources.md#aws) 只提供重试/幂等设计的工程参考，不证明 LibTV 有幂等键、取消或任意任务查询。[核验记录](../evidence/02-verification.md)中的原生探针尚未执行；本例仅演练其目标条件与失败边界。
